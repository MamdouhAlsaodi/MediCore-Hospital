# Phase 5 Quickstart and Acceptance Scenarios

**Purpose:** Planned reviewer journey only. Do not run until implementation is explicitly authorized and completed.

## Prerequisites

- Java 21 and Maven 3.9+ (or the project’s verified containerized Maven toolchain).
- Docker with Compose, PostgreSQL client, Node/npm.
- Disposable local resources only.
- Process-local synthetic credentials generated by the Phase 5 harness.
- No protected runtime env files.

## Planned canonical command

```bash
scripts/phase5/acceptance.sh
```

Expected terminal semantics:

- `0`: every required Phase 5 gate passed.
- `1`: a required gate failed; fail-fast.
- `2`: required capability missing; report `BLOCKED`, never PASS.

## Scenario 1 — Hierarchy and context matrix

1. Start a clean review stack with one network, three hospitals, two or more branches per hospital, and at least two time zones.
2. Authenticate as network administrator.
3. Fetch `GET /api/network/hierarchy`; verify deterministic hospitals/branches.
4. Switch to Hospital B / Branch B2 through `POST /api/auth/context`.
5. Verify replacement session includes organization, hospital, branch, role, scope, and assignment.
6. Attempt Hospital C’s branch under Hospital B assignment; expect generic denial and zero mutation/audit success.
7. Disable the selected branch in a disposable fixture and reuse token; expect immediate invalidation.

## Scenario 2 — Network patient identity

1. Under Hospital A, create synthetic patient `MRN-P5-0001`.
2. Verify Hospital A receives one patient ID.
3. Switch to Hospital B before transfer acceptance; search and direct read must not reveal it.
4. Create and accept a transfer to Hospital B.
5. Verify Hospital B now resolves the same patient ID through an active access grant.
6. Verify Hospital C still cannot discover it.
7. Race duplicate patient creation; assert one identity and one stable conflict.

## Scenario 3 — Transfer happy path

1. Source actor in Hospital A creates REQUESTED transfer for an active synthetic admission targeting Hospital B.
2. Destination actor lists the request; unrelated Hospital C cannot discover it.
3. Destination accepts with Branch B1 and an available bed plus an idempotency key.
4. Verify transfer is ACCEPTED, bed has one active reservation, destination access exists, and one audit event is stored.
5. Repeat identical accept command with same key; verify no duplicate rows and same semantic result.
6. Source starts transit; source handoff and bed release follow the defined transaction.
7. Destination completes; destination admission exists, reservation is CONSUMED, bed is OCCUPIED, transfer is COMPLETED.
8. Verify command-center totals and audit chain.

## Scenario 4 — Transfer rejection and cancellation

- REQUESTED → REJECTED by destination: no reservation, no destination patient access created by transfer.
- REQUESTED → CANCELLED by source: no reservation.
- ACCEPTED → CANCELLED: only the transfer-owned reservation is released; any pre-existing destination access is not revoked.
- Any command after a terminal state returns `409` and writes no success audit.

## Scenario 5 — Concurrency and idempotency

1. Run two destination accept commands for the same bed and separate transfers concurrently.
2. Assert exactly one succeeds and one receives `409`.
3. Assert one ACTIVE reservation, no partial state, and no false success audit.
4. Reuse one idempotency key with a changed payload; expect `409`.
5. Repeat concurrency test enough times to expose locking/constraint races without sleeps.

## Scenario 6 — Capacity and command center

1. Query branch capacity under Branch A1.
2. Query Hospital A capacity under hospital scope; verify exact sum of active branches.
3. Query network dashboard under network admin; verify exact sum of hospitals and branches.
4. Verify inactive hospital/branch and foreign rows do not contribute.
5. Switch context while an old dashboard response is delayed; verify old numbers never render.

## Scenario 7 — Browser journey

Desktop and mobile viewports must cover:

- Login and visible network/hospital/branch context.
- Hierarchical selector with loading, denial, single-target, and multi-target states.
- Patient search before/after destination access grant.
- Transfer create, destination review, accept, transit, complete.
- Conflict display for a raced bed.
- Hospital/network dashboard drill-down.
- Audit evidence.
- Context switch render isolation.

Screenshots/traces remain scratch diagnostics on failure unless a separate public evidence task sanitizes and explicitly publishes them.

## Scenario 8 — Migration rehearsal

1. Apply V1..V7 to empty PostgreSQL; restart with zero pending migrations.
2. Restore a Phase 4-shaped synthetic fixture at V4.
3. Apply V5..V7.
4. Verify all prior branches map to `LEGACY-HOSPITAL-001`.
5. Verify all valid patients have network ownership and one hospital access grant.
6. Verify malformed orphan/mismatched fixtures fail before non-null/constraint completion.
7. Verify source data remains unchanged after a refused rehearsal.

## Acceptance evidence checklist

- Exact backend/frontend/E2E totals and exit codes.
- Flyway applied/failed/pending counts.
- Hierarchy authorization matrix.
- Patient identity/access proof.
- Transfer lifecycle and race proof.
- Idempotency proof.
- Capacity sum invariants.
- OpenAPI/client drift proof.
- Public-artifact scan.
- Zero leftover Phase 5 containers, networks, volumes, databases, or temporary evidence directories.
- FR/SC traceability with `PASS | PARTIAL | BLOCKED`.
